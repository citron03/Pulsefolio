# Pulsefolio 라이브러리 선정 기준

## 목적
Pulsefolio는 "기능 과시"보다 "운영 가능한 투자 모니터링 제품"을 목표로 한다. 따라서 라이브러리 선택도 개발 속도보다 운영 안정성과 유지보수성을 우선한다.

## 프로젝트 성격
- 실제 거래/체결 기능은 제외
- 준실시간 데이터 모니터링 중심
- 개인/소규모 팀이 지속 운영 가능한 구조 필요
- UI 신뢰성(상태 처리, 오류 대응, 접근성) 중요

## 선정 원칙
1. 안정성 우선
- 최근 릴리즈 활동이 있고, 실사용 레퍼런스가 충분한 라이브러리 채택
- 보안 취약점 대응 가능 여부(`audit`, patch cadence) 확인

2. 단순성 우선
- 같은 문제를 해결하는 도구가 중복되지 않도록 최소 세트 유지
- 도입 후 러닝커브/설정 복잡도가 과도하면 제외

3. 운영성 우선
- 장애/에러 상태를 숨기지 않고 표준 UI로 드러내기 쉬운 도구 선호
- 로깅/테스트/검증 자동화와 궁합이 좋은 도구 선호

4. 확장성 우선
- 현재는 Mock/준실시간이지만 API 실연동 시 구조가 유지되는 도구 채택
- 컴포넌트/상태/차트가 독립적으로 교체 가능해야 함

## 영역별 기준

### UI 컴포넌트
- 기준: 접근성 내장 + 스타일 자유도 + 과한 디자인 강제 없음
- 선택: `@headlessui/react`
- 이유: 금융 톤에 맞는 커스텀 디자인이 가능하고 접근성 기본기가 탄탄함

### 스타일링
- 기준: 빠른 구축 + 토큰 기반 일관성 + 팀 내 가독성
- 선택: `tailwindcss v4` + CSS 변수 토큰
- 이유: 유틸리티 생산성과 도메인 색상 규칙(수익/손실/상태)을 동시에 관리 가능

### 차트
- 기준: 대시보드형 시각화 적합성 + 러닝커브 + 유지보수 용이성
- 선택: `recharts` (기본)
- 대안: `lightweight-charts` (트레이딩형 고밀도 차트 필요 시)
- 이유: 현 단계는 도넛/라인/스파크라인 중심이므로 Recharts가 비용 대비 효율적

### 상태관리
- 기준: 서버 상태/클라이언트 상태 분리 가능성
- 선택: `React Query + Zustand` (도입 예정)
- 이유: polling/stale 제어와 UI 상태 분리가 명확해 운영 이슈 대응에 유리

### 품질 도구
- 기준: 자동화 가능성 + 팀 일관성 + 속도
- 선택: `Biome`, `TypeScript strict`, `Vitest`, `Playwright`, `Husky`
- 이유: 작은 팀에서도 품질 하한선을 자동으로 유지 가능

## 제외/보류 기준
- 실시간 체결/호가 전용 고복잡도 라이브러리
- 설정 대비 실효성이 낮은 과도한 메타 프레임워크
- 유지보수 중단/릴리즈 정체 라이브러리

## 의사결정 체크리스트
새 라이브러리 도입 전 아래 질문을 통과해야 한다.
- 이 라이브러리가 기존 도구와 역할이 겹치지 않는가?
- 장애/상태 처리 UX를 더 일관되게 만들 수 있는가?
- 3개월 뒤 유지보수 비용이 증가하지 않는가?
- 제거(rollback) 비용이 감당 가능한가?

3개 이상 "아니오"가 나오면 도입을 보류한다.
