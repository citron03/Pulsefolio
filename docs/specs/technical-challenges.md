# Pulsefolio 기술적 챌린지 문서

## 목적
이 문서는 Pulsefolio가 기술적으로 어디에 도전하고 있으며, 어떤 기준으로 구현 우선순위를 잡는지 명확히 기록한다.

## 핵심 기술적 챌린지

### 1. Polling 기반 준실시간 처리
- WebSocket 중심 구조가 아닌 polling 기반으로 시세 갱신을 설계한다.
- 장중/장종료/휴장 상태를 반영해 갱신 주기를 동적으로 제어한다.
- 호출량 과다와 사용자 체감 지연 사이의 균형을 맞춘다.

### 2. 금융 서비스형 데이터 상태 UX
- 모든 데이터 영역에서 `loading`, `empty`, `error`, `stale` 4상태를 일관되게 처리한다.
- 오류를 숨기지 않고 재시도, 마지막 갱신 시각, stale 경고를 명시한다.
- 신뢰감을 해치지 않는 메시지 톤과 시각적 피드백 규칙을 유지한다.

### 3. 도메인 계산 정확성 보장
- 평가금액/손익/수익률 계산을 UI에서 분리하고 공통 계산 모듈로 관리한다.
- 평균단가, 보유수량, 현재가 변경 시 재계산 일관성을 유지한다.
- API 누락값(PER/EPS 등)은 `N/A`로 안전 처리한다.

### 4. 운영 현실 대응 설계
- API 승인 지연, 레이트리밋, 분봉/재무 데이터 제한을 전제로 설계한다.
- Mock 우선 개발로 UI/도메인 로직을 독립 검증한다.
- 데이터 소스 장애 시 graceful degradation(기능 축소 운영) 전략을 적용한다.

## 기술적 중점

### A. 범위 통제
- 거래/체결/자동매매/계좌연동 등 규제·인프라 고비용 영역은 의도적으로 제외한다.
- "많은 기능"보다 "완성도 높은 핵심 경험"을 우선한다.

### B. 안정적인 아키텍처
- Next.js App Router + Route Handlers(BFF)로 단일 코드베이스 내에서 프론트/백엔드 역할을 통합한다.
- React Query + Zustand로 서버 상태와 UI 상태를 분리한다.
- 외부 API 연동은 adapter 계층으로 캡슐화해 교체 비용을 낮춘다.

### C. 검증 가능한 품질 기준
- LCP 3초 이내, 리스트 virtualization, interval 해제 누락 방지 등 비기능 요건을 명문화한다.
- 계산식/상태전이/오류처리 중심 테스트를 작성한다.

## 성공 판단 기준
- 장 상태 전환(장전/장중/장후/휴장)이 정확히 반영된다.
- polling 정책이 호출 비용과 사용자 체감 신선도를 모두 만족한다.
- 핵심 계산값(평가금액/손익/수익률)에 불일치가 없다.
- 장애/빈 데이터/오래된 데이터에서도 사용자 신뢰를 잃지 않는 UI를 유지한다.
