# Pulsefolio 모바일 제품/배포 계획

## 목적
Pulsefolio의 모바일 계획은 화면 반응형뿐 아니라 배포 채널, PC/모바일 버전 관리, 운영 검증 기준까지 포함한다.

초기 전략은 **단일 Next.js 코드베이스 + 반응형 웹 + PWA 대응**이다. PC 버전과 모바일 버전을 별도 제품으로 분리하지 않고, 같은 도메인/같은 API/같은 인증 흐름에서 화면 밀도와 내비게이션만 다르게 제공한다.

앱스토어 배포는 첫 릴리즈 범위가 아니다. 푸시 알림, 홈 화면 설치, 오프라인 스냅샷, 생체 인증 같은 네이티브 요구가 명확해진 뒤 PWA 또는 Capacitor 래퍼로 확장한다.

## 배포 전략

### Phase 1: 반응형 웹
- 배포 채널: Vercel Production (`main`)
- 사용자 진입점: 동일 URL
- 관리 방식: 하나의 Next.js 앱에서 CSS breakpoint와 컴포넌트 레이아웃으로 PC/모바일 대응
- 목표: 모바일 브라우저에서 투자 상태 확인 가능

### Phase 2: 설치형 PWA
- 배포 채널: 동일 Vercel URL + Web App Manifest + Service Worker
- 사용자 진입점: 모바일 브라우저 또는 홈 화면 설치
- 관리 방식: 웹 릴리즈와 동일한 CI/CD를 사용하고, PWA 관련 파일만 추가 관리
- 목표: 앱처럼 실행되는 모바일 경험, 마지막 스냅샷 캐싱, 네트워크 오류 시 stale 표시

### Phase 3: 네이티브 래퍼 검토
- 후보: Capacitor 기반 iOS/Android 래퍼
- 조건: 앱스토어 배포가 실제로 필요하거나, OS 푸시/생체 인증/앱 배지/공유 시트 등 네이티브 기능이 필수일 때
- 관리 방식: `apps/web`와 `apps/mobile-shell` 같은 구조로 분리하는 시점에 별도 의사결정
- 제외: 거래/주문 기능, 인증 없는 민감정보 저장, 시장 상태를 무시한 백그라운드 polling

## PC/모바일 버전 관리 원칙
- PC와 모바일은 별도 브랜치로 관리하지 않는다.
- 기능 플래그를 쓰더라도 도메인 로직과 API 계약은 공유한다.
- 화면 차이는 컴포넌트 레벨에서 관리한다. 예: `DashboardDesktopLayout`, `DashboardMobileLayout`
- 도메인 계산, polling, stale 판단은 공통 hook/service에서 관리한다.
- 릴리즈 노트는 하나로 작성하되, 모바일 영향이 있으면 `Mobile` 항목을 별도로 둔다.
- QA는 PC Chrome, 모바일 375px, 모바일 430px, 태블릿 768px을 같은 릴리즈 게이트에 포함한다.

## 모바일 UX 목표
Pulsefolio의 모바일 화면은 데스크톱 대시보드를 축소하는 방식이 아니라, 투자자가 이동 중에 가장 먼저 확인해야 하는 상태와 숫자를 빠르게 읽는 구조로 설계한다.

기준 뷰포트는 375px이며, 430px, 768px, 900px 이상 구간에서 점진적으로 정보 밀도를 높인다.

## 모바일 우선 정보 우선순위
1. 시장 상태와 마지막 갱신 시각
2. 총 평가금액, 총 손익, 총 수익률
3. 데이터 상태(`loading/empty/error/stale`)
4. 보유 종목 Top 5
5. 주요 지수와 관심 종목
6. 자산 비중/추이 차트

모바일 첫 화면에는 1~3번이 반드시 들어와야 한다. 차트는 첫 화면의 보조 정보로 밀어내고, 숫자/상태를 먼저 보여준다.

## 레이아웃 원칙
- 375px: 단일 컬럼, 카드 간격 12px, 화면 padding 16px
- 430px: KPI 2열 구성 허용, 숫자 카드의 높이는 동일하게 유지
- 768px: 차트와 목록을 순차 배치하되 탭으로 정보 밀도 조절
- 900px 이상: 현재 데스크톱 그리드처럼 KPI 4열과 차트 2열 사용

보유 종목 테이블은 모바일에서 가로 스크롤 테이블을 기본으로 두지 않는다. 핵심 열만 카드형 행으로 재구성한다.

모바일 보유 종목 카드 기본 필드:
- 종목명/코드
- 현재가
- 수익률(▲▼ + 색상)
- 평가금액
- 미니 추이

평균단가, 보유수량, 메모 등은 상세 진입 또는 확장 영역에서 제공한다.

## 컬러 적용 계획
현재 프로젝트 토큰을 그대로 사용한다.

- 배경: `--pf-bg-0`, `--pf-bg-1`, `--pf-bg-2`
- 카드/패널: `--pf-surface-1`, `--pf-surface-2`
- 본문/보조 텍스트: `--pf-text-1`, `--pf-text-2`
- 인터랙션: `--pf-accent-1`, `--pf-accent-2`
- 상승/수익: `--pf-profit`
- 하락/손실: `--pf-loss`
- 보합: `--pf-flat`
- 상태 배지: `--pf-live-*`, `--pf-closed-*`, `--pf-warning-*`, `--pf-danger-*`

모바일에서는 장식 색상을 줄이고 상태 색상을 우선한다. 배경 그라데이션은 유지하되 카드 투명도와 그림자는 약하게 사용한다. 상승/하락은 색상만 쓰지 않고 `▲`, `▼`, `-` 기호를 항상 함께 표기한다.

## 상태 처리
모든 모바일 데이터 블록은 다음 상태를 동일한 위치와 톤으로 표시한다.

- `loading`: 카드 내부 skeleton. 레이아웃 높이는 유지한다.
- `empty`: 안내 문구와 다음 행동을 한 줄로 제공한다.
- `error`: `--pf-danger-*` 톤, 재시도 버튼을 제공한다.
- `stale`: `--pf-warning-*` 톤, 마지막 갱신 시각을 같이 표시한다.

시장 상태가 `장 종료` 또는 `휴장`이면 자동 갱신을 강조하지 않고, 마지막 스냅샷 기준임을 명시한다.

## 인터랙션 원칙
- 탭/필터/상태 토글의 최소 터치 영역은 44px 이상
- 주요 액션은 하단 고정 버튼보다 컨텐츠 근처의 명확한 버튼을 우선
- 거래/주문을 암시하는 CTA는 만들지 않는다
- 가로 스크롤은 차트 또는 보조 테이블에만 제한적으로 허용
- 핵심 숫자는 긴 단어/큰 금액에서도 줄바꿈 또는 축약 표기로 깨지지 않게 한다

## 검증 기준
- PC/모바일이 같은 API 응답과 계산 로직을 사용
- Vercel Preview에서 PC와 모바일 breakpoint를 함께 검증
- PWA 단계에서는 설치 가능 여부, 아이콘, splash, offline fallback 확인
- 375px, 430px, 768px, 900px에서 레이아웃 겹침 없음
- 첫 화면에서 시장 상태, 총 평가금액, 손익/수익률 확인 가능
- 색상 없이도 수익/손실/상태 의미를 이해 가능
- `loading/empty/error/stale` 상태가 모바일에서도 카드 높이 급변 없이 표시
- 100개 보유 종목 목록은 virtualization 또는 점진 렌더링 적용

## 구현 순서
1. 반응형 웹 기준 확정: 모바일 토큰 보정, padding, gap, 카드 radius, 그림자 강도 정리
2. 대시보드 KPI와 상태 패널의 375px 레이아웃 확정
3. 보유 종목 Top 5를 모바일 카드 행으로 전환
4. 지수/관심종목/차트 섹션을 탭 또는 접힘 구조로 정리
5. Playwright로 PC/375px/430px/768px/900px 스냅샷 검증
6. PWA 도입 판단: manifest, 아이콘, offline fallback, stale cache 정책 설계
7. 앱스토어 배포 판단: 네이티브 요구가 생긴 경우에만 모바일 래퍼 별도 계획 작성
